# Characters

## Characters (component-based, inherited scenes)

`scenes/characters/character_base.tscn` is the shared base: a `Character` root (`scripts/characters/character.gd`, thin `CharacterBody3D`) over the visual subtree (`SkinManager` `%BodyContainer` rig + AnimationTree), `%HurtBox`, `AimTarget`, and the shared components. `player.tscn` and `enemy.tscn` INHERIT it and add their own components. Naming convention (also the `scripts/components/` folder split): **`Character*` = shared** (`CharacterMovement` — locomotion physics/pace, subclasses supply intent via `gather_intent()`; carries a WEDGE TRIPWIRE (`watch_for_wedge`): a live body pushing somewhere and going nowhere for 2s prints a one-line `DBG WEDGED` state dump — a "player stuck at the loot boxes" report could NOT be reproduced from geometry (`stuck_probe` sweeps 50 spots around both box pairs, all walk free; the first sweep's total freeze turned out to be the scavenger shooting the probe's player dead mid-run — a corpse ignores intent), so the next wedge in the wild names its own mechanism; `CharacterAnimator` — writes AnimationTree parameters, `play_death()` swaps to the raw clip on the sibling AnimationPlayer; `CharacterWeapons` — inventory/equip/hold pose plus the mechanical fire/reload cycle (`can_fire`/`fire_shot`/`reload` — cooldown, ammo, shot clip, `bloom` accuracy-loss/recovery; trigger DECISIONS live in the variants), `setup()` duplicates each WeaponData so magazines aren't shared between characters — and an EMPTY loadout arms FISTS (`data/items/weapons/melee/fists.tres`, type `MELEE_UNARMED`, an invisible WeaponMelee scene in the hand): a weaponless brain otherwise chases into melee range and stands there staring. MELEE swings through `can_strike`/`strike(target)` — clip picked from the type's `attacks` list, the blow landing at `STRIKE_CONNECT` of the clip and ONLY if the target is still inside `STRIKE_REACH` then, so stepping back out of a punch dodges it; damage goes straight to the target's hurt box (no hitbox sweep yet). The unarmed set deals only the punch — the kick is wired in the blend tree but nothing calls for it, since the upper layer filters to arm/chest bones and a leg-less kick reads as a spasm (`unarmed_probe` covers the arming, the landed blows and the swing cadence; `unarmed_pose_probe` covers the blend-tree wiring those clips need to be SEEN, which was missing until 2026-08-17 — see the upper-layer note below); `CharacterFootsteps`), **`Player*` = player-only** (`PlayerMovement` — input polling over CharacterMovement; `PlayerAim` — cursor facing, chest `LookAtModifier3D`, camera aim-lead; `PlayerWeapons` — input over CharacterWeapons: cycling, aiming, firing, reload, accuracy spread; `PlayerInteractions` — the 6m sphere that NOTICES offers, so no prop carries a shape just to advertise itself, see UI.md), **`Enemy*` = enemy-only** (`EnemyMovement` — `move_to(position)`/`stop()`, pathfinds via the scene's `NavigationAgent` when a navmesh exists and steers straight otherwise; RVO avoidance is on (`avoidance_enabled` + `velocity_computed`, one tick behind) so dynamic obstacles the navmesh can't know — the car carries a `NavigationObstacle3D` — bend the path instead of wedging the enemy; the steering direction is LOW-PASSED (`steer_direction` slerp) and re-paths are gated to >1m target drift, because RVO and near-equal routes around an obstacle flip the chosen side at frame rate and an unfiltered rig head-shakes left-right; a give-up watchdog (`gave_up`: no net displacement for 1s while navigating) declares unreachable destinations (a spot under the parked car) reached so states move on, and CharacterMovement only faces its intent while ACTUALLY moving, so a blocked body never head-shakes with steering flips; `EnemyWeapons` — the AI trigger over CharacterWeapons (`weapon_layer = 1` hits the player hurt box): `fire_at(target)` branches MELEE first — a swing only starts inside `STRIKE_REACH` (chase's advancing fire calls this on a timer too, and fists have no suppressive range), and the attack state's fire gate goes through `trigger_aligned`, which for melee checks the BODY's facing instead of the barrel (fists have none) — otherwise fires from a clamped chest-band height inside the weapon's accuracy cone (`spread_factor` + shared bloom + a `move_penalty` scaled by locomotion pace, so shots on the run are ~2x wider — mirrors the player's pace term), semi-autos throttled by `fire_pause`, AUTOMATICS burst — trigger held until `burst_release` accuracy is lost (bloom gain scaled by `recoil_factor`), squeezed again at `burst_resume`; auto-reloads on empty; a fresh engagement arms a FIRST-SHOT MISS that fires only if the target's rig isn't facing the shooter (the player's rig follows the cursor, so unaimed = unaware); `EnemyAI` — the brain: builds a code-driven `StateMachine` (`scripts/state_machine/`) at ready with `guard`/`patrol`/`roam`/`chase`/`attack`/`investigate`/`cover` states (`scripts/components/enemy/states/`). THE IDLE IS CHOSEN by `home_state()` (`roam` beats `patrol_route`, else guard) and every combat state's fallback `return_state` resolves through it — the literal "guard" defaults are gone, which is what lets an interrupted patroller come BACK to patrolling. PATROL walks a `PatrolRoute` (`scripts/world/patrol_route.gd`: a node whose Marker3D children are the stops in tree order, looped; a marker's +Z is the dwell facing — the rigs' forward — and `dwell` is the stand time), sweeping the guard's look-around at each stop and resuming from the NEAREST stop after an interruption; a blocked stop is skipped via the movement give-up, never shoved through. ROAM is the scavenger idle: drift to the nearest `loot_container` not yet picked over, rummage a few seconds facing it, move on, and start the round over when all have been seen — window-shopping only, it never rolls a crate's loot. game.tscn carries the first world enemies: a survivalist on the 4-stop `RidgeLoop` around the ridge crate and `scavenger.tres` (lumberjack, pistol, `roam = true`) working the crate circuit, both configured through editable-children overrides on the instanced `EnemyAI`; guard holds/returns to the post and facing (captured on the first PHYSICS frame, not `_ready` — spawners add_child before placing, which would post the enemy at the scene origin) with idle look-around sweeps (and turns toward the suspicion suspect), chase sprints toward the target with ADVANCING FIRE (single suppressive shots on a 0.7-1.5s timer inside full effective range; the rig faces the target instead of the travel direction — both point the same way while closing — so the chest aim can land the muzzle) and hands to attack inside `attack_range()` (80% of weapon effective range, melee 2m), attack fires after a 0.4s aim settle with combat FOOTWORK (owns facing via `face_movement = false`: strafes between bursts, backpedals when crowded or reloading) and falls back to chase on lost range or a 0.6s grace after losing sight (flicker doesn't whip the brain); taking a hit or starting a reload requests COVER (`try_cover`, 6s retry lockout on failure) — cover sprints to the spot, crouches behind it to reload and drain bloom, leans out to the peek to burst, tucks back, and ABANDONS it (back to attack) when rushed inside 4m, when the threat moves somewhere the spot no longer blocks, after two peeks that produced no shot, or after 12s — cover is only held while it still works; investigate opens with a 0.4s reaction beat (face the clue, then walk); the rig faces the target squarely while `EnemyAim` does the fine aim, and shots only leave once the LIVE barrel (weapon-local +X, `EnemyWeapons.barrel_error()`) is within the fire gate; `EnemyAim` — drives the base scene's chest `AimLook`/`AimTarget` exactly like PlayerAim (same per-weapon `aim_yaw_offset` calibration; the invisible `AimTarget` marker is easy to delete by accident in the editor and losing it silently disables ALL aiming — `Utils.resolve_aim_target()` recreates it and rewires the modifier at runtime, with a warning): idle gazes down the rig's forward (the raw aiming hold pose points gun+head ~50° sideways otherwise), combat locks onto the AI's `aim_at()` focus. Losing track rushes the last-seen spot, then INVESTIGATE walks the quarry's `CharacterTrail` breadcrumb by breadcrumb (`EnemyAI.quarry` remembers who) until the scent goes cold, looks around 2s, then RESUMES the interrupted state; re-spots while engaged don't re-arm the miss; `Character.damaged` engages too — chase heads to the attacker's position with NO miss owed (they shot first), every hit STAGGERS the aim (`EnemyWeapons.stagger`: bloom spike + trigger hold), and a fresh hit while searching re-points chase (`redirect`); a fresh engagement SHOUTS `Signals.alert_raised(source, quarry)` — allied enemies within 30m join the hunt toward the quarry; `Character.died` disables the brain; `EnemyLoot` — the corpse as a storage (2026-08-13): on `died` it builds a small `Inventory` over `data/storage/body_pockets.tres` (5x2) — the hands' own duplicated WeaponData instances move in WHOLE, live magazines riding (nothing conjured, the ammo-economy rule), plus a 2-6 round pinch of each gun's calibre (`max_ammo > 0` gates it, so a machete seeds no rounds; fists are name-skipped) and 0-2 draws off an optional `LootTableData` using LootContainer.fill's stateful-instance rule in miniature. Its authored `SearchArea` (an `InteractiveArea` on the BODY ROOT, not under the plain-Node component — a Node3D under a non-Node3D anchors at the world origin) starts `enabled = false` and death arms it only if the pockets hold anything (conditional advertising); `open` emits `Signals.container_opened` titled by the body's `first_name`, so looting IS the trunk/locker panel, and the first search sets `spent` — hollow dot, the crate's rule. Corpses are deliberately unsaved, so neither is this. `corpse_probe` (characters/, 11)). `CharacterVision` (shared — companions will reuse it): an Area3D whose sphere (radius synced from `CharacterData.vision_range`, local-to-scene shape) broadphases candidates — CHARACTERS and VEHICLES (mask 104) — and targets any HOSTILE one. Hostility is faction-based and re-checked PER FRAME, not at area entry (`Character.is_hostile_to()` accepts anything exposing `get_faction()`; a vehicle reports its driver's faction, -1 driverless = nobody's enemy; spotting an occupied car resolves `EnemyAI.quarry` to the DRIVER so the trail hand-off survives a bail-out); a target's own hull doesn't block LOS of it. Nearest hostile visible wins; ACQUISITION is instant only inside the detection ring (non-sneaking) — cone sightings fill a SUSPICION gauge first (fast up close, slow at the cone edge, x2 slower vs sneaking, `suspect` exposed for the guard's turn-and-look tell), and an `alertness` dial (1.0 in/after combat, 45s fade) speeds spotting x5 and doubles the ring — re-approaching a spooked guard is harder; a SNEAKING target slips under the detection ring and must be in the cone proper — crouching doesn't beat eyes — a held target is retained peripherally (`retains()`: `CharacterData.combat_range` ~a screenful — beyond the acquisition sphere — plus LOS, no cone), so neither aiming, strafing, nor an on-screen sprint away breaks a fight; LOS blocked by walls/car, `spotted`/`lost` signals. `CharacterCover` (shared, on the enemy scene): samples rings of navmesh-snapped candidates and returns the best `{spot, peek}` pair — the spot's shot line to the threat must be BLOCKED and a sidestep peek must have a clear one, both raycast at fire height (1.1m), scored by travel distance with a penalty for giving ground. `CharacterTrail` (shared, in the base scene — every character leaves scent): a breadcrumb ring buffer of {position, time} samples (0.5s interval, 1m min move, 12s lifetime) read by trackers. `character.gd` discovers components by TYPE (child `is CharacterMovement` etc.), applies `CharacterData` (skin, speed, health, weapon inventory), and handles basic death (`die()`: dead clip held as corpse pose, collisions/components off). A node in the `player` group registers itself with `InputManager` and grabs the camera. The base scene's `%HurtBox` is INERT (layer 0, non-monitorable) — each variant must override it or shots pass through: player → layer 1, enemy → layer 2, both monitorable. Exercised in the `_tools/gym/gym.tscn` sandbox (the gym's `Player` node IS the player.tscn instance — probes should target it rather than spawning a second player, which would also steal `InputManager.player`).

## The dodge (`character_dodge.gd`, `player_dodge.gd`, 2026-08-17)

SHARED ON PURPOSE, because enemies are meant to learn it: `CharacterDodge` owns the whole act — the committed hop, the i-frames, the energy and the cooldown — and the variants decide only WHEN. `PlayerDodge` is the input layer (SPACE and the pad's A — the face button the interact move to X freed) and the two things only a player can be mid-way through: it refuses with a barrel in the arms (the refusal drinking already makes) and spills a drink in progress. An enemy needs nothing but the component and three wired siblings; `dodge_probe` proves it by building one onto the gym enemy at runtime, unwired battery included, because a "shared" skill that has never run outside the player is a guess.

THREE PIECES CARRY IT, none of them new machinery. `CharacterMovement.dash(direction, distance, duration)` is the travel: authored as a DISTANCE and a DURATION, so the launch is solved from them (`d = v * t / 2`, bled linearly to nothing) rather than being a speed multiplier nobody can picture, and it runs through the same `move_and_slide` as a walk — a wall stops a roll like it stops everything. While `dash_left` lasts, the hop OWNS the velocity and intent is zeroed: steering a dodge would make it a walk in a costume, and the zeroed intent is also what keeps the rig from turning mid-roll. `HurtBox.immune` is the i-frames, and it is TWO things at once because one is not enough: the FLAG swallows what is already on its way (a tracer's hit is scheduled on a flight timer, and melee calls `hit()` straight past the layers), while dropping the LAYER makes new rays miss outright so the shot carries on to the wall behind instead of stopping dead in a body it cannot hurt. It covers exactly the right set through that one gate — shots, swings, grenades and a car's ram all arrive via `hit()`, while `PlayerHeat` burns through `take_damage` directly, so the sun is not dodgeable. `CharacterAnimator.play_dodge` fires the clip (below).

THE ORDER AT DEATH IS A TRAP: `die()` clears `immune` BEFORE zeroing the layer, because the flag's own setter hands back the layer it borrowed — a roll that ended after death would otherwise restore a LIVE hurt box on a corpse. `dodge_probe` kills the enemy mid-roll and re-checks the layer after the window for exactly this.

Knobs are component exports (`distance` 3m, `cooldown` 1.2s, `energy_cost` 12 of 100 — about eight rolls on a full battery, against 45s of sprint), not `CharacterData` knob/span dials: nothing wants per-character tuning yet. THE CLIP IS THE CLOCK — `duration()` reads `dodge_forward`'s length (0.4s), so retiming the animation retimes the i-frames and the travel with it. `PlayerWeapons` yields the trigger mid-roll the same way it yields to a readied throwable, and `finish()` re-poses the hands ONLY if the upper layer is still the roll's (`upper_weight <= 0.0`) — a drink or throw begun mid-roll has claimed the arms and cutting it off would be a second bug.

## Animation

A DODGE IS FULL-BODY, so it CANNOT be an `upper_state` input: on the arm/chest layer the legs would keep walking through the roll. It rides a `dodge_shot` `AnimationNodeOneShot` inserted between `upper_blend` and `output` (fed by a 4-input `dodge_state` transition over the four `dodge_*` clips), which is the FIRST thing in this tree to sit on the output — anything else that must override the whole body belongs beside it, not in `upper_state`. Two mechanics of the hand-edited resource, both learned here: `input_N/name` GROWS a transition (there is no `input_count` line to write, but the name must come first for each N), and a fresh `transition_request` is only read on the tree's next process, so a probe that checks `parameters/dodge_shot/active` in the same frame reads false on a working dodge. The clip's reach is measured on the HIPS, the one bone `upper_blend`'s filter leaves alone, with the travel dialled down to 5cm so locomotion cannot be what moved them: 0.507 of pose against a 0.003 idle drift.

Characters share one animation library (`assets/animations/character/`, 100+ `.tres` — many not wired up yet: spellcasting, blocking, sitting, skeleton-specific). The `AnimationTree` setup uses transition/one-shot parameters addressed by the string constants in `character.gd`; animation names for melee attacks follow `state_0..2` random-pick convention. UPPER-LAYER CLIPS MUST BE TRANSITION INPUTS: `set_upper_animation` names an input of the blend tree's `upper_state` node, so a library clip that was never added there does nothing — new clips need a `AnimationNodeAnimation` subresource, an `input_N`, a `nodes/anim_*` entry AND a `node_connections` pair in `character_blend_tree.tres`. ALL FOUR, and the `input_N` is the one that lies: a name with no connection behind it is a fully valid transition target that the tree accepts and then writes NOTHING for, and because `upper_blend` filters to the arm/chest bones, nothing written means those bones KEEP THEIR LAST VALUES. It does not fall back to a rest pose or to locomotion — the hands FREEZE on whatever state was connected before, so the symptom is history-dependent and looks like anything but a wiring fault. The fists shipped that way from the start (2026-08-17): inputs 11-13 were named `melee_unarmed_idle`/`_attack_punch_a`/`_attack_kick` with no subresource, no `nodes/anim_*` and no connection, so a bare-handed character wore the pose of whatever it had last holstered and a punch never moved the arm at all. `unarmed_probe` passed throughout, because `CharacterWeapons.strike` deals the blow on a timer off `get_clip_length`, which reads the LIBRARY directly and never touches the tree — the damage was always right, only the picture was wrong. `unarmed_pose_probe` (characters/) now measures the wiring two ways: structurally, that every name in `CharacterWeapons.UPPER_ANIMATIONS` reaches a connected input (9 names, all types), and behaviourally by ROUTE-INDEPENDENCE — one destination state reached from two different departures, which is the only way to tell a pose from a leftover. Unwired the fists' idle landed 0.17m apart by route against a 0.004m floor measured on a known-wired input, and the punch sat 0.002m from the idle (the same frozen pose, no swing); wired, both collapse to the floor and the punch throws the hand 0.29m clear.

## Humanoid base (the Zombies kit rig, 2026-09-22)

`scenes/characters/humanoid_base.tscn` replaces the KayKit base for Dead Ride. Same component tree, different rig: the Zombies kit's Mixamo-named skeleton renamed to the `SkeletonProfileHumanoid` bone names and exposed as `%GeneralSkeleton`. The scene is generated by `_tools/asset_extractor/build_humanoid_base.tscn` (run it as a scene through `verify.sh`; it needs the autoloads) from the old base minus the rig, so a rebuild overwrites hand edits.

Animation reuses the KayKit library through Godot's import retarget. Both sides are mapped onto the humanoid profile in their `.import` files (`_not_exported/animations/Rig_Medium_*.glb`, restored from Nowhere's history, and `_not_exported/Zombies_parts.blend`), with `fix_silhouette` and `overwrite_axis` on both so the rests agree, and `remove_tracks/unmapped_bones` on so the KayKit-only `hand.*` and `handslot.*` bones leave no tracks the mixer would fail to resolve. `extract_animations.gd` then pulls the clips into `assets/animations/humanoid/` under the old names and builds `humanoid_library.tres`; `humanoid_blend_tree.tres` is the old tree with its filters on the profile bones. Measured on `running_a`, the leg swings 2.49 rad on the new rig against 2.47 on the old.

Bodies are outfits. `OutfitManager` dresses an `OutfitData` (`data/outfits/*.tres`, a list of part stems like `body_a_1`; the slot is the last non-numeric token) from `assets/meshes/humanoid/parts/`. The parts are extracted from `Zombies_parts.blend`, not `Zombies.blend`: in the master file each of the 245 part objects sits on a layout grid and the export bakes that object location into the vertices, so the dressed character rendered as scattered pieces until a Blender pass zeroed every part location into the parts-only copy. `CharacterData.body_path` points at the outfit resource.

Attachments: hand slots ride the kit's `RightHandProp` and `LeftHandProp` bones at identity (weapon grips were posed for the KayKit slots and need re-tuning), `AimLook` sits on `Chest`. Scripts naming bones use `Utils.rig_bone()` with both names and find the skeleton by type. The kit characters stand about 1.5 m tall against KayKit's 1.1 m, so capsule, hurt box and any height constants calibrated on the old rig are suspect. Probes: `humanoid_base_probe` and the windowed `humanoid_base_shot`.
