# Inventory

## Inventory (`scripts/inventory/`, `scripts/components/character/character_inventory.gd`, `scenes/ui/inventory/`)

`Inventory` (RefCounted, not a Node — characters and vehicles both own one and it is probe-testable headless) places rectangles over a `StorageData` mask: `can_place`/`place`/`add`/`move`/`remove`/`find_free_spot`/`entry_at` plus the kind-wise withdrawal pair `count_of`/`take` (over `ItemData.same_kind`; the garden's seed spending), occupancy as a `Vector2i -> InventoryEntry` Dictionary so a check costs the footprint, not a scan. `can_place(..., p_ignore)` is what lets `move` overlap an entry with itself. `find_free_spot` is row-major, so items settle top-left. `InventoryEntry` = `{item, origin}`, held by IDENTITY so quick slots track an item as it moves.

`CharacterInventory` (shared component) is the carried-items authority: the grid from `CharacterData.backpack.storage`, plus `quick_slots` sized `BackpackData.slots` (6 — 2 weapon + 4 item, the pack panel's trays) whose FIRST TWO are the weapon slots. THE SLOTS ARE REAL STORAGE since the panel revamp (2026-08-10), not references into the grid: a slotted stack lives on its slot alone with `origin == InventoryEntry.NO_CELL`, `equip` MOVES a weapon out of the grid (displacing the occupant back into it, refusing outright when the pack can't take the displaced one — with real storage an overwrite is item destruction, so there is no overwrite), `assign_quick_slot(entry, slot, from)` is the one mover (grid→slot, slot→slot swap type-checked BOTH ways, container→slot via the drag payload's `source`), `stow_slot` pours a slot back into the grid keeping the remainder on a short pour, and `clear_slot` is BOOKKEEPING ONLY — for after the stack has already moved (a landed drag, the last grenade thrown); calling it on a stack that hasn't moved destroys the stack. `ammo_entries` spans grid AND item slots, so ammo parked on the bar still counts as reserve and reloads still find it. The save (v2) writes each slot as its own row through the static `Inventory.save_row`/`load_row` pair — the v1 scheme saved slots as indices into the grid's entry array, which died the moment slots stopped being proxies. It duplicates the starting `WeaponData` once and hands those same instances to `CharacterWeapons.set_weapons()` — the non-duplicating half of `setup()`, split out precisely so equipping from the pack can't hand back a full magazine. Characters WITHOUT the component (enemies today) still arm straight from `CharacterData.weapon_inventory` via `setup()`. It is also the AMMO ECONOMY: `setup()` points `CharacterWeapons.carried` back at itself, and from then on every round a magazine gains is taken OUT of the grid (`draw_rounds` → `spend_ammo`) — the starting magazines included (`load_magazines`), so the loadout's granted stacks are the whole allowance and nothing is conjured the first time a gun is drawn. That is what keeps the quick slot's `magazine/reserve` pair summing to the rounds actually carried: firing destroys a round, reloading only moves one. A short reserve tops off partially and an empty one refuses the reload outright (`can_reload`). A character with no pack (`carried == null`) has no reserve to draw down, so enemies still fill for free — the same two functions, one branch. `PlayerInventory` adds input only (number keys → `select_slot`, Q/E → `cycle_weapon` over the filled weapon slots, V → `holster`); it owns the number keys and weapon cycling that used to live in `PlayerWeapons`, so the bar's highlight always matches what's in hand. CONSUMABLES (`ConsumableData`, first item `data/items/consumables/field_bandage.tres`) ride the same selected-slot pattern as throwables: `PlayerConsume` (component beside `PlayerThrow`, same `carried` wiring) claims the attack button whenever a consumable sits on the ACTIVE quick slot (`held_item()` is the shared reading of that — the active ITEM slot's item, null while a weapon is drawn or the bar is holstered; the WORLD asks it too, since a crop spot tells pouring from harvesting by whether the can is in hand rather than by owning a second interaction point) — even at full health, where `begin_use` refuses rather than burns one, so a misclick is never a gunshot. USING IS NOT INSTANT (2026-08-12): the `use_item` clip owns the whole act — `begin_use` poses the upper body and starts a timer off the clip length, and ONLY `finish_use` heals/restores (`Character.heal` clamped, `PlayerEnergy.restore`), dents the stack, and holds a 0.3s recover beat. ANY DAMAGE MID-DRINK CANCELS: `PlayerConsume` connects to `Character.damaged`/`died`, and a cancelled sip restores nothing and burns nothing — the user's rule. The clip had to be WIRED as an `upper_state` input (nodes + input_14 + connection in character_blend_tree.tres); being in the library alone animates nothing, the throw's exact lesson, and `consume_probe` now guards this input the way `throw_probe` guards its two. TWO ENTRY POINTS: pressing a consumable's QUICK-SLOT SHORTCUT is the use (one press selects and drinks — `PlayerInventory` cancels any drink on every slot press/holster first), and the pack grid's right-click Consume closes the screen and calls `begin_use(item, entry, inventory)` — the grid path dents ITS OWN stack on completion, tolerating the stack having moved meanwhile. A consumable WITH a model rides the hand while selected (`ConsumableData.get_held_scene()` returns `model` — the water bottle; the bandage has none and leaves the gun drawn), which also means modeled consumables now AUTO-SLOT at setup like any held item. Drag-onto-the-bar remains the other assignment path. THE HAND RETURNS TO WHAT THE DRINK DISPLACED: `begin_use` captures the weapon drawn right now (the grid path), else `prop_return_slot` — written by `select_slot` at the moment a held item takes the hand, where EMPTY HANDS ARE A REAL ANSWER (-1), never a gap to fill from an older memory. The first cut used `holstered_slot` as the fallback and a player who drank bare-handed got V's gun from ten minutes ago pushed into their hands; the two memories are separate on purpose (V's keeps its toggle contract — a drawn gun displaced by a held item still feeds it). `settle_hand` re-selects the capture when the act ends, finished OR cut — and RECORDED EMPTINESS IS A DESTINATION: anything short of a live weapon slot lands on `CharacterInventory.bare_hands()` (prop gone, nothing drawn, `active_slot` -1, V's memory untouched — a new primitive, because `holster()` TOGGLES and called with empty hands it draws the old gun, the exact opposite). So nobody stands around holding an empty bottle, getting shot hands the gun straight back, bare hands return to bare, and a SPARE bottle left on the slot stays slotted rather than climbing back into an empty hand. THE SOUND RIDES THE SAME RULES: `ConsumableData.use_audio` carries the act's audio (the bottle's `drink.ogg`; null is silent — the item brings the sound the way `SurfaceData` brings footsteps), one scene-authored `AudioUse` player under PlayerConsume emits it (the `AudioWeaponSwap` precedent — the EMITTER is the character, since the bandage has no prop to attach a sound to), `begin_use` starts it, a finished act lets it ring out, and `cancel_use` stops it dead — a cut sip is silent the way it is unspent. That return is also why `consume_one` finds its slot BY ITEM, never by `active_slot`: by the time the clip ends the return may already have drawn the weapon, and denting the active slot then eats the gun (`energy_probe` caught exactly this — the SMG got drunk). The board's water/energy half waits on the Energy system. Holstering must release the CHEST LOOK-AT as well as the model (`PlayerWeapons.holster` overrides to zero `aim.stance_weight`): the ranged hold poses ARE the aiming clips (`idle == aim`, so hip-fire lands on the reticle), which means carrying a gun holds the look-at wide open at the weapon's `aim_yaw_offset` — left on with empty hands it aims a weapon that is not there and the character walks looking ~34° to one side. RELOADING is the opposite case: the look-at stays OPEN — dropping `stance_weight` there un-twists the torso out of `aim_yaw_offset` into the reload clip and back, a ~52° measured swing on the rifle that read as the character turning away to reload (`reload_twist_probe` guards it; measure such things POST-modifier via a BoneAttachment3D — `get_bone_global_pose` reads the raw clips and cannot see the look-at). `apply_pose()` cannot do it; it returns early once there is no weapon to pose. Equally, `HandSlot` EMPTIES ITSELF in `_ready`: characters are authored with a weapon already in the hand to pose the hold in the editor (player.tscn carries a Pistol), and nothing owns that at runtime — `set_weapon`/`holster` only ever track the model they instantiated, so it sat in the hand forever, holstered or not, inside whatever was drawn next.

ENERGY (`PlayerEnergy`, component on player.tscn) is the survival battery: sprint gulps (~2.2/s), walking sips (~0.35/s scaled by pace), standing is free. EMPTY IS EXHAUSTED, never damage — it pulls `CharacterMovement.sprint_allowed` and sets `fatigue_scale` 0.7 (both new hooks the base movement applies; enemies keep the defaults) — and sprint only returns at `recover_threshold` (10), a hysteresis so the key doesn't flutter at the empty mark. `Signals.energy_updated` drives the EN bar above HP (`EnergyInfoUI`, a clone of the HP row pending Figma). `ConsumableData` restores health AND/OR energy, and `PlayerConsume.begin_use` refuses only when NOTHING the item restores is short — a bottle at full energy refuses, thirst at full health still drinks. The Water Bottle (+40) is the baseline refill, and the restore lands at the END of the use_item clip, never at the press. SLEEPING (`Bedroll`, placeholder-primitive prop beside the locker, "Sleep until morning") lands on tomorrow 08:00 and refills the battery — which is what forced `Calendar.set_time` to compare MINUTES-of-day, not hours: sleeping at 08:06 used to rewind six minutes instead of rolling the day (exactly-equal stays a same-day no-op so the F9 scrub can't leap a day). THE NIGHT IS WATCHED, NOT SKIPPED (2026-08-12): `SleepTransition` (`scenes/ui/menus/sleep_transition.tscn`, LAST child of game.tscn's Overlay, `process_mode = ALWAYS`, registered as `Globals.sleep_transition` the way CameraFollow registers) pauses the tree under a translucent scrim and SWEEPS the clock to morning over ~3.5 real seconds — `DayNightCycle` is ALWAYS too, so the sun genuinely arcs — stepping `Calendar.time_data` whole minutes per tween tick with ONE `calendar_updated` emit per tick, so listeners (the crops' midnight loop included) see time only ever advance, exactly the multi-day emissions they already handle. The readout goes through `Settings.format_time`, never a hardcoded clock. `Bedroll.sleep` now only force-drops a carried barrel and delegates; `wake()` is morning itself — `set_time` (the sweep arrives standing on the wake minute, so it is the exactly-equal no-op there), the refill, the save, IN THAT ORDER at the END of the night, never at the press — and a scene WITHOUT the overlay (probes, the gym) wakes on the spot through the same `wake()`, the old jump exactly. Being last child, its `_unhandled_input` fires first and swallows everything while running, so TAB cannot open the pack mid-night. `sleep_probe` (ui/, 9 checks: pause under the overlay, nothing landed at the press, the clock genuinely mid-sweep, morning whole, the save written, the world released); `energy_probe` (14, drain/exhaustion/water/sleep) keeps the direct path honest.

`holster()` TOGGLES: putting the weapon away clears `active_slot` so no slot reads as active, and the slot it came from is kept INTERNALLY in `holstered_slot` (from `equipped_slot()`, not `active_slot` — a utility slot can be selected while a gun is still drawn) so pressing V again draws the same gun. The bar therefore has ONE state, `set_active`, rather than a separate equipped marker. Two traps this closes: `setup()` must seed `active_slot` from `equipped_slot()` (`push_weapons` draws a gun but never selected a slot, so the bar opened with nothing lit), and `push_weapons()` must re-apply a deliberate holster afterwards — `set_weapons` draws slot 0 whenever the hands are empty, which is right on the FIRST arming and would otherwise let any bar rearrangement undo the holster. A HOLSTERED START is AUTHORED, not hacked: `CharacterData.current_weapon_idx = -1` (the player's .tres sets it) makes `CharacterInventory.setup` holster right after arming — weapons keep their slots, the hands open empty over the unarmed reticle dot, V draws — and only the pack path honors it, because an enemy has no draw step in its brain yet and must always open armed (commenting the `equip` inside `set_weapons` was tried for this once and disarmed every enemy into a chase-and-stare).

UI: `BackpackScreen` (TAB, in game.tscn's `Overlay`, `process_mode = ALWAYS`, `hide()` in `_ready` for the same editor-saves-it-visible reason as `SettingsScreen`) pauses, blurs and frees the mouse. The pack side is `backpack_panel.tscn` (`BackpackPanelUI` extends `ContainerPanelUI`, an INHERITED scene so the shared header/grid stay one authorship), which adds the mockup's two slot trays between title and grid: WEAPON SLOTS (2 × 256×128) and ITEM SLOTS (4 × 128), each tray a 2px `#6A807B` outline at radius 24, each slot a sunken `#E1D9AD` box bordered `#BBBFA1` at radius 12. The slot widgets REUSE `quick_slot_ui.gd` (`backpack_slot.tscn` — same script, panel styles, no key cap, mouse STOP where the HUD bar's are IGNORE); the slot id is passed EXPLICITLY into `setup` because the panel spreads six slots over two trays where `get_index()` means nothing. Hovering a filled slot raises the same tooltip card the grid items get (`slot_hovered` up through the screen); right-click stows. The HUD bar (`QuickSlotsUI`) is GAMEPLAY-ONLY now — `visible = not paused`, always mouse-inert — the panel owns every slot interaction, which retired the bar's drag-to-assign and its backpack_state juggling. `InventoryGridUI` instances `inventory_cell.tscn` from the mask — LOCKED CELLS ARE NEVER BUILT (the old hatch shader is deleted); the mask reads through the SHAPE of the open cells, tracked in `cell_map` (which also replaced the index-math lookup `show_footprint` used, since child indices no longer follow grid maths). Seams are SINGLE-DRAWN per the mockup's 2px lines: every cell owns its left+top edge and closes right/bottom only against the outside — two neighbours each drawing a full border reads as a doubled 4px line. The silhouette's CONVEX corners round (radius 12): a cell corner rounds iff BOTH edge-neighbours across it are missing, which rounds the outer silhouette and leaves inner steps square — the mockup's exact rule, verified by pixel-walking the render. It lays `inventory_item.tscn` widgets at `origin * 128` sized `size * 128`; the GRID owns hit-testing, not the cells, because one item spans several. WITH TWO CONTAINERS OPEN, F or a double click on the hovered item FERRIES it across (`BackpackScreen.transfer` — F only means "equip" in the solo pack view): the receiving side runs `Inventory.add` semantics, so stacks top up their kind first, overflow opens new cells, and whatever finds no room STAYS in the source entry. Drag-and-drop merges the same way when the drop lands ON a matching stack (`merge_target` reads the stack under the CURSOR, not the footprint origin) — cap-aware, overflow hunts free cells, and a quick slot is only released when the whole stack actually left it. Leaving the PACK for a container routes through `CharacterInventory.drop` so quick slots and an equipped weapon let go correctly; `transfer_probe` (ui/) covers all of it. A THIRD PANEL TYPE joined them (2026-08-12): `PlantingPanelUI` (extends `ContainerPanelUI`, so header/grid/`setup` stay one authorship) is the crop plot's one-cell planting slot plus a status line and a PLANT button, opened by `Signals.planting_opened(plot, spot)` exactly as a container opens on `container_opened`. Only ONE panel may stand beside the pack, which is what `beside()` answers — every test that asked `container_panel.visible` (the layout, F's ferry, the context menu's Transfer row, `backpack_state_changed`) asks it instead, so the planting slot inherits drag, double-click, F and Transfer for free. THE SLOT IS REAL STORAGE, the quick slots' rule again: what rests in it is OUT of the pack and belongs to nothing that saves, so `release(pack)` pours it back on EVERY exit — the close button, TAB, and a container opening over it — while planting spends only the seed claim and lets the surplus ride out on that same close. The round trip always fits because nothing can enter the pack while this panel is the one beside it. The single cell is enough because every seed claim fits one stack (light 20 of 80, medium 15 of 60, heavy 5 of 20) — a species costing more than its ammo's `max_stack` would be unplantable here, which is a real constraint on Economy balance. `panel_width` gained a `custom_minimum_size` floor for it (one cell is 256 wide and a PLANT button is not); the pack's authored 896 happens to equal what its 6-wide grid already computed, so no existing layout moved. `planting_probe` (ui/, 15) drives the station's real garden through it. An item widget carries the Figma GridItem component's two states — Default and Hover (16px radius, Hover adding a 4px `Palette.BLUE` border) — but the FILL is the item's rarity colour dimmed per state (`darkened(0.36)` / `darkened(0.12)`), because the component has no rarity axis; the styleboxes are authored in the .tscn for geometry and duplicated at `setup()` for the tint. `ItemTooltip` renders entirely from the `ItemData` virtuals, F equips / X drops. `QuickSlotsUI` is its OWN CanvasLayer (layer 2) so the bar stays sharp above the HUD — GAMEPLAY-ONLY since the pack panel grew its own slots: the test collapsed to `visible = not paused` (every screen pauses, so this catches screens nobody has written yet), the bar is permanently mouse-inert, and the pack panel's slot widgets own every interaction the bar used to host in the pack view. The layer runs `PROCESS_MODE_ALWAYS` purely so it still ticks to notice the pause flip, which SceneTree has no signal for. A CARRIED BARREL hides the bar too (`Signals.carry_state_changed` → the same `apply_visibility`): the hands are full and every draw refuses, so a lit bar would advertise keys that do nothing — see Desert.md's carry paragraph for the refusal gates. `Signals.backpack_state_changed(is_open, with_container)` carries both bits because BackpackScreen is the authority on which view is up — listeners must not infer the container from `container_opened`, which reaches the screen and the HUD in scene order, not view order, and must key CLOSED on `is_open` ALONE: `open_container()` emits `(true, false)` mid-open, before its panel shows (the trunk-lid audio slammed during opening until it did). The trunk sounds live on `vehicle_base.tscn` (`AudioTrunkOpen`/`AudioTrunkClose`, `PROCESS_MODE_ALWAYS` because opening the trunk pauses the tree the same frame — an inheriting player would hold the open sound until the screen closed and fire it stacked on the slam); `Vehicle.open_trunk` plays one and remembers `trunk_open`, the `backpack_state_changed` listener plays the other. weapon slots draw 192px wide against utility's 128. A weapon slot carries the MAGAZINE readout the HUD used to: one `magazine_pip.tscn` (6x24, radius 2) per round of `max_ammo` in an `HBoxContainer` floating 7px ABOVE the box (`offset_top = -31`, centre-aligned so any magazine length stays centred), spent rounds dimmed with `modulate.a = 0.3` rather than a second stylebox — every state on this bar is one shape at two alphas, `set_active` included. The slot's number is therefore the RESERVE ALONE (`ammo_count()`): loaded rounds have already left the grid, so a 20-round magazine off a 100-round stack reads `40 loaded pips + "80"`. The strip is only rebuilt when the slot changes weapon; firing just re-alphas it. Note the pips assume `max_ammo * 8 <= slot width` — true up to 24 rounds on a 192px weapon slot, so a bigger magazine would need a thinner pip. All metrics are the Figma mockup's literal pixels — the project viewport is 3840x2160, the same as the design frame. Item icons render (WINDOWED only — a headless run's dummy rasteriser saves blank images) into `assets/textures/thumbnails/<source folder>/` at `size * 128`: weapons render their `model` scene, tools a bare `mesh` on the data — laid sideways ONLY for a wide icon box (an upright mesh already fills a tall one; the 1x2 jerrycan stays standing). THE LOOK LIVES IN ONE FILE, `_tools/asset_extractor/icon_rig.gd` (camera/light/framing/pose AND the export — `render_png` is the single path everything ships pixels through; render subjects are MANNEQUINS — process disabled, RigidBodies frozen — because the grenade's throwable physics had it obeying gravity: falling out of the studio frame and rendering pixels low even across the batch pass's two frames), and the ONE TOOL is `icon_studio.tscn` (the editor toolbar's "Scenes" dropdown — the `addons/scene_menu` plugin, a hand-picked dict plus the auto-scanned probe submenus — opens it; the standalone batch renderer was absorbed and deleted: B in the studio, or `-- --all` headlessly, re-exports every icon FROM DISK — cache bypassed, so unsaved studio tweaks never leak — and quits when done without --shot). Per-item pose is DATA and each item's is its own — a preset layer was tried and REMOVED (real items each wanted unique settings): `ItemData.icon_yaw/icon_pitch/icon_roll/icon_zoom`, an "Icon Render" export group every render path honors, so a full re-export never loses a tuned angle. The pose rides a pivot node above the laydown, and the model is RE-CENTERED on that pivot by its visual bounds (`offline_bounds` — a hand-accumulated transform walk, because `global_transform` is an ERROR on nodes not yet in a tree): scene origins are authored for gameplay (a weapon's is its grip), and rotating around one swings the mesh in an arc instead of spinning it. The STUDIO: clickable item list, mouse-drag rotates IN PLACE (SHIFT SNAPS to 15° — arrows nudge 5° and snap the same way with Shift), wheel/Q/E zoom, SLIDERS for all three axes at 15° detents plus zoom (exact repeatable poses; they and the Reset/Save/Export All buttons mirror the R/ENTER/B keys, all `focus_mode` NONE so clicking one never steals the arrows from the model), and the drawn FRAME is the png's exact limits with the 128px cell divisions inside it. While the mouse is DOWN the auto-fit FREEZES (re-fitting per angle read as the item rushing the camera) and re-tightens on release. Ctrl+arrows edit `ItemData.size` itself — the icon size IS the grid footprint, and the png follows on save. ENTER writes the .tres (`save_keeping_uid`, which rewrites the file Godot-canonical — defaults drop out) and renders the png in the same stroke, dirty state starred. `-- --item= --yaw= --zoom= --save --all --shot` drives it headless for verification. The centering shifted every icon's absolute coordinates, so png hashes moved once by SUB-PIXEL AA noise — visually identical, verified by eye; byte-comparison only proves runs against the same baseline.

## No ammo economy (2026-09-22)

The reserve is gone by design: guns never run out. `CharacterWeapons.draw_rounds` returns whatever a reload asks for, `can_reload` is always true, and `CharacterInventory.load_magazines` fills a fresh weapon from its `max_ammo` instead of spending the pack. Magazines and reload times stay, so the only gunfight variables are fire rate and reload time. `spend_ammo`/`ammo_count` remain on the pack as ordinary stack helpers and ammo items are still stackables, but nothing consumes them; the empty-click banner always reads RELOAD, and `notification_probe` asserts that. Loot from kills is upgrade material or cash, never rounds.
