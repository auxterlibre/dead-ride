# UI

## UI (`scripts/ui/`, `scenes/ui/`)

HUD lives inside `game.tscn` (CanvasLayer): health bar, vehicle speed + fuel-tank readout while driving, clock + date (top-right), contextual input prompts. `DeathScreen` (`scripts/ui/menus/death_screen.gd`, `Overlay/DeathScreen`, `process_mode = ALWAYS`): listens on `Signals.player_died` (the BUS, so no deferred player-hook and a reloaded scene rewires itself) — the world fades to grayscale over an UNPAUSED corpse beat (a screen-space shader driven by a tweened intensity), the scrim lands and pauses the tree, then title/Respawn/Quit fade in; respawn reloads the current scene, so autoload state (clock, purse) survives and the world resets. Death's penalty is the save rollback; other reactions belong on the same bus signal. Its probe re-points `get_tree().current_scene` at the game (root-parented) first — reloading the current scene from a probe otherwise reloads the PROBE, forever. There is NO bottom-left weapon/ammo panel — the magazine moved onto the quick slot itself (see Inventory below). PER-WEAPON RETICLES exist now: `reticle.tscn` carries one hand-designed Control child per `Enums.WeaponClass` (AssaultRifle/Shotgun/SMG/Pistol/Revolver/SniperRifle — the class enum's RIFLE arm is the sniper), all edge-anchored inside the sizing Control so the existing spread-scaling works on every shape unchanged, and `Reticle.show_for` switches visibility on `Signals.weapon_setup` — re-declared `(weapon)`, a WeaponData or NULL, which `PlayerWeapons.holster` now emits. Empty hands — and any class WITHOUT a designed child yet (melee) — fall back to the bare `Unarmed` dot (the sniper's centre piece alone), so the hidden OS cursor always has SOME mark under it. The scene ships with a design-time child visible, so `_ready` runs `show_for(null)` rather than trusting the flags — same rule as the screens' hide-in-ready. `reticle_probe` (ui/) covers the switching AND audits every ranged .tres's `weapon_class` — which caught the sniper cloned from the assault rifle still carrying class 3: its tooltip had read "Assault rifle" unnoticed the whole time. All driven by `Signals` — UI never reaches into gameplay nodes.

`InputKeyButton` (`scenes/ui/input_key_button.tscn`) is the Figma component behind every key prompt AND every screen button — it is a real `Button`, so prompts are clickable, unlike the passive corner labels. Metrics are the mockup's literal pixels (272x96 for TAB/Close, 16px padding all round, 16px gap, radius 11, badge 104x64 radius 6, JetBrains Mono Bold 40). The fill is deep-space-blue at **55% alpha** (dark-cyan on hover, the same 0.549 scrim the HUD bars already use) and Pressed is Hover at 0.9 scale, so it is designed to sit OVER THE WORLD, not on a light panel: on custard the disabled state (custard 15% bg / 30% badge+text) is invisible. That is why the Settings buttons live OUTSIDE the panel on the blur, matching where the Backpack's close button already sat. `input_action` resolves the badge from the InputMap so a rebind moves it — with a keycode fallback, because Godot's built-in `ui_*` actions carry no PHYSICAL keycode and report "(UNSET)".

THE BADGE FOLLOWS THE HAND (2026-08-17): with a pad live the lettered badge is REPLACED by the controller's own art (`assets/textures/icons/input/xbox/`, a `TextureRect` beside the label in the same row, one visible at a time) — the icons ARE badges, cream disc and glyph, so they stand in for the styled Label rather than sitting on it, and disabled dims them by alpha since they carry their own colours. Resolution is `InputManager.icon_for(action)` / `icon_for_key(key)`, keyed on the LABEL `key_for` already resolves a control to ("A", "LT", "LS", "L3"), so ONE table serves art and text and a control with no icon simply keeps its lettering — a null icon is an answer, not a failure. The kit covers all 18 controls the map uses (face, bumpers, triggers, both sticks and their presses, view/menu, the four d-pad directions), so the lettering path is now only reached by an action with NO pad event at all (`weapon_slot_0`); the probe asserts BOTH — that every polled action wears art, and that the unbound one still gets none. THE GATE IS THE LIVE DEVICE, NOT THE STRING: labels collide across devices, "A" being both the pad's bottom face button and the key under `move_left`, so `icon_for_key` returns null whenever `pad_active` is false. `CharacterPromptsUI` now passes the input ACTION to each prompt as well as the resolved key, so a button can re-badge itself; that is belt-and-braces for world prompts (a device switch runs `refresh_prompts`, which withdraws the old key's prompt and raises a NEW button for the new one — a probe holding the old reference finds it freed) and load-bearing for the SCREEN buttons, which persist across the switch and re-badge in place off `Signals.input_device_changed`. The icons import at `svg/scale = 2.0` so a 32px source rasterises to the badge's authored 64px instead of being upscaled. `gamepad_probe` (ui/, 28) carries the claims, including that every name in the table is on disk — the table cannot drift from the folder — and an end-to-end swap driven by REAL events through `Input.parse_input_event`, not by writing `pad_active` by hand. `pad_shot` (ui/, 5) is the pixel half, and it is the only shot in the suite that runs with a pad live. TWO TRAPS ARE BURIED IN IT, both of which made a working badge read as broken: `get_viewport().get_texture().get_size()` is NOT the size of the image `capture()` returns (1707x960 against a 2560x1440 frame), so a crop computed from it lands out on the open sand — take the scale off the captured image; and the prompt column is RE-ANCHORED to the player every frame, so a badge-sized crop measures the badge SLIDING under a drifting camera (0.0177 of "idle" change, as much as the swap itself) until `CharacterPromptsUI` is frozen with `process_mode = DISABLED`. Cropped to the opaque badge with the layer pinned, the swap measures 0.5865 against a 0.0024 floor.

THE CORNER CHANNEL FOLLOWS THE HAND TOO (2026-08-17): the bindings decision the old note here waited on landed as the `car_*` actions — `car_accelerate` (W / RT), `car_reverse` (S / LT), `car_brake` (Shift / B) — so `Vehicle.enabled_drive_input` now resolves through `key_for` instead of `action_get_events(...)[0]`'s always-keyboard event 0, remembers the key arrays it raised in `drive_prompts`, and re-badges on `input_device_changed` mid-drive (connected seated, disconnected on exit) by withdrawing EXACTLY those arrays — the corner list is keyed by them, and a device switch would otherwise strand the old device's labels. The steer pair collapses to one badge when both keys resolve to the same stick ("LS"), which is the collapse the old note feared, handled instead of hit. Steering itself stays on `move_left`/`move_right` — they already carry the stick.

OFFERS REVEAL IN TWO STAGES (`InteractiveArea.stage`): anywhere inside an area shows a quiet HINT DOT floating at the interaction point (`Signals.interaction_hint_added/removed` → the `InteractionHints` layer in hud.tscn, unprojected like the prompts), and the KEY PROMPT only registers within `prompt_range` (2.2m) with the rig turned toward the point (`prompt_angle` 55° off `body_container` +Z). THE DOT RIDES BOTH STAGES — it is the feed-forward, so the mark spotted from across the sand has to be the same mark walked up to; it gains an OUTER STROKE next to the key rather than handing over to it, and the hint signals therefore fire on OFF↔anything, never on the HINT↔PROMPT step. Which look stands is read per frame off the source the signal handed over, exactly as its anchor position already was: `stage == PROMPT` puts the ring up, and `InteractiveArea.spent` — the generic "this offer has already been taken", which `LootContainer` sets on itself once searched — swaps the solid core for a HOLLOW one, so a picked-over desert reads at a glance. All four looks are authored as three panels in `interaction_hint_dot.tscn` (`Ring` / `Solid` / `Hollow`, 24px core inside a 64px ring) and `InteractionHintDot.show_state` only picks which stand. THE LOOKS ARRIVE RATHER THAN APPEARING (2026-08-12): a new dot pops in on a back-ease overshoot with a quick fade, the ring opens wide and closes onto it as it fades in, and both run backwards on the way out — but the VISIBILITY FLAGS STAY INSTANT and only `scale`/`modulate` animate, which is what lets everything above keep reading `show_state` per frame. That per-frame call is the constraint the whole thing had to be built around: `show_state` is called EVERY frame off the source, so it now acts on the CHANGE alone — a tween restarted sixty times a second never leaves its first frame. Scale rides the dot's ROOT, whose size never changes, because the layer positions the dot off its own `size` each frame and scaling a sized rect would drag it off its anchor (both root and ring carry an authored `pivot_offset`, or a Control scales from its top-left corner). The exit needed the opposite of what the layer did: `remove_hint` used to `queue_free` the dot on the spot, leaving nothing to animate — the dot is now HANDED OVER to a `leaving` list and frees ITSELF when its tween ends, and `InteractionHintsUI.visible` counts `leaving` as well as `dots`, since hiding on an empty `dots` would cut the exit of the very dot that emptied it (walking away from the only offer, i.e. the common case). A leaving dot stops being repositioned, which a twelfth of a second never shows; a re-noticed offer spawns a fresh dot beside the fading one rather than reviving it, which only the un-hysteresised 6m notice boundary can produce. COLLAPSED IS A THRESHOLD, NOT A ZERO: Godot clamps a Control's `scale` to CMP_EPSILON (1e-5), so a probe asserting `is_zero_approx()` on a scale it just set to zero lands exactly on that strict-`<` boundary and reads false. ONE POINT IS ONE OFFER. Props used to stack several on a single spot — the bedroll's sleep+save, a crop spot's plant+water, the pump's three — which is several dots painted on top of each other and several keys for one thing to walk up to. The rule now is one interaction per point, and where a point genuinely has several jobs they are chosen either BY CONTEXT (the crop spot reads the hand: a can in the active quick slot means pour, empty-handed means plant or harvest) or by a MENU (`Signals.interaction_menu_requested`, the delivery truck's counter) — never by a second area. The bedroll simply lost its save offer (sleeping is the save). `InteractionHintsUI` still groups dots by anchor snapped to 0.25m and folds the group into one (ringed if ANY is in reach, hollow only once ALL are taken): it is the backstop for props placed on top of each other, not a licence to stack offers. The gas pump is the one holdout — its nozzle, can fill and till are still three areas on one point, pending the design where the player PICKS UP the nozzle and the actions follow what is in hand. AN OFFER IS A POINT AND TWO NUMBERS — no shape, no physics, nothing to author twice. It used to be an Area3D with a hand-drawn reach box, and that box was wrong twice over: it was SMALLER than `prompt_range` on every single prop (a crate's was 1.2m against the 2.2m knob), so the knob was dead code and the two-stage reveal could never happen; and a shape is invisible at runtime, so nobody could see what they were tuning anyway. Now `prompt_range` IS the reach — distance from the point, flat, plus `prompt_angle` off the rig's forward — and NOTICING is one radius on the player: `PlayerInteractions` (`scripts/components/player/player_interactions.gd`, a plain Node on player.tscn, `notice_range` 6m) walks the `InteractiveArea.offers` registry each frame, sets `player_near` and ticks `update_stage()`. A registry rather than physics, the way `CoolArea` registers into `PlayerHeat.pockets`: a point cannot be a collision shape, and ~25 distance checks a frame is not worth a broadphase. Setting `player_near` fires `noticed`, which is where owners recompute conditional offers (`GasPump`'s can fill, `CropSpot`'s label) — it lands BEFORE the stage is judged, so the old "the area's own enter-refresh reads `enabled` a frame too early" trap is gone by construction. Per-prop reach is now a NUMBER in the inspector, measured from what each shape used to cover: crates 1.8, bedroll 1.9, locker 1.3, crop spot 1.0 (tight, because spots sit 1.5m apart and share the interact key), the car's door 1.3 and its trunk/nose 1.6, the truck's counter 3.5, everything else the 2.2 default. Driving is the one hole in a sensor that lives on the player: `enter_vehicle` sets `process_mode = DISABLED`, so the sweep would stop with the offers frozen mid-advert — `PlayerInteractions` listens for `Signals.drive_state_changed` (a signal still lands on a disabled node) and sweeps them off. WHAT A RADIUS CANNOT SAY is which side of the prop you stand on; the car's door box used to. If that starts to matter, the fix is `InputManager` picking the NEAREST offer for a key rather than the most recently registered — not a shape coming back. Hysteresis (+0.6m/+30° while shown) stops boundary flicker, a HELD offer LATCHES while its key is down so a pour never drops because the rig drifted, and standing ON the point (a garden spot underfoot) counts as facing it. `refresh()` re-pushes a shown prompt's label; `retract()` in `_exit_tree` keeps a freed area from leaking its dot or prompt. The precision this buys is that spatially disjoint offers can SHARE the interact key instead of stacking F/G/H. `interaction_probe` (ui/, 31 checks) covers the ladder, the car's points, the popup menu, and the dot's animation — that it starts collapsed and lands exactly on its resting size, and that a removed offer's dot outlives it on the `leaving` list with the layer still up.

THE PAD LAYOUT IS A CONTRACT WITH `gamepad_probe` (2026-08-17, the full-pad pass): X interacts and equips, A dodges (and confirms in menus), B reloads (brakes seated, backs out of menus), Y taps between the two weapon slots and HELD (0.4s, fires on release for the tap so a draw never precedes a holster) goes bare-handed — the pad's holster, `holster`'s own pad event is gone — the DPAD picks the four item quick slots directly (up/right/down/left = slots 2-5, and a consumable's press IS the drink, the same one-press rule the number keys follow), triggers fire/aim on foot and throttle/reverse seated, SELECT is the backpack, R3 is build mode, START pauses. `next_item`/`prev_item` lost their dpad events (Q/E still cycle), and `toggle_weapon` is pad-only — keyboard hands already have six number keys. EVERY control the map polls wears an icon (25/25), so the lettered-badge path only serves actions with no pad event at all. MENUS ARE B-CLOSABLE AND DPAD-WALKABLE THROUGHOUT: `ui_accept`/`ui_cancel` carry A and B as PROJECT OVERRIDES — Godot 4.7's defaults put dpad+stick on the four directions but NO pad buttons on accept/cancel, a fact `pad_menus_probe` pins so a lost project.godot block cannot pass silently. Focus is the navigation model (`MenuActionButton` and `InputKeyButton` wear their hover look as the focus stylebox; world prompts opt OUT with `FOCUS_NONE` so a menu's walk cannot wander into the HUD), grabbed on open only when `pad_active`; the settings rows are not buttons, so `SettingsScreen` walks them itself (`focused_row` over `eligible_rows()`, left/right `nudge()`s the focused cycler or slider in 5% notches, shoulders page the tabs raw — LB/RB's world action names have no business in a menu), with `SettingsRow.focused` feeding the same wash `hovered` does. The pack already had ui_* grid-cursor movement; it gained B-close and A-as-F (equip, or ferry when a second panel stands beside). `QuickNotification` (HUD) is a DUMB DISPLAY (the user's rule, 2026-08-18 — a first cut had it deriving copy from bus state and was corrected): it renders whatever `Signals.notification_requested(text, Enums.MessageType)` hands it, and every threshold lives with its EMITTER — `PlayerWeapons.announce_empty()` reads the reserve and picks RELOAD or OUT OF AMMO, `PlayerHeat` banners SCORCHING SUN as its burn starts, `PlayerEnergy` warns STAMINA LOW once per dip (20% raise, 30% re-arm, `low_warned`). The panel's only behaviours are display behaviours: a repeated message extends the stay instead of re-popping, and death clears it (`notification_probe`, 10). The quick-slot bar hides seated (`drive_state_changed`), the same one-gate rule its carrying flag follows.

INPUT PROMPTS HAVE TWO CHANNELS, chosen per offer by `Enums.PromptPlacement` on `Signals.input_info_added(keys, label, placement, input_action)`. CHARACTER (the default for `InputManager.create_interaction`) draws `InputKeyButton`s beside the player via `CharacterPromptsUI` — `camera.unproject_position` rather than a Sprite3D, so they stay crisp and reuse the screens' own buttons; it runs `PROCESS_MODE_ALWAYS` purely so it can notice `get_tree().paused` and hide, since every screen pauses. CORNER is the quieter standing-help list (`InputInfoUI`, bottom-right, unfilled labels): the driving controls and EXIT VEHICLE, which is corner-placed because the driver sits inside the car where a pinned prompt would be under the roof. `InputManager.active_inputs()` SORTS, so prompts stack interact → _secondary → _tertiary instead of in whatever order the physics step reported the areas. Clicking a prompt calls `InputManager.try_to_interact`; `InputManager.pointer_over_prompt` makes `PlayerWeapons` hold fire while the cursor is on one, because firing is POLLED and the GUI swallowing the click would not stop the shot.
